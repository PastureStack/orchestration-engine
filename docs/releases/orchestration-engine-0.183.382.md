# Orchestration Engine 0.183.382

This source candidate repairs false API Key authorization denials in the native load-balancer Agent lifecycle. Agent setup runs before `Instance.agentId` is written, and its private Agent account and `agentApiKey` do not have the caller's project account. The resolver now proves the exact native Factory relationship instead of treating those internal principals as ordinary project resources.

The supported callers retain their original operation: direct load-balancer create, update/activation, upgrade/rollback and the necessary retirement cleanup, plus Stack `activateservices` for an inactive load balancer. A Stack caller must resolve through the verified Instance/Agent and a unique persisted expose map to a load balancer in that exact authorized Stack and project. Native removal covers Agent deactivation/removal, its primary or authorized secondary Agent accounts, and their Agent credentials. Captured cleanup can finish after its exact parents are removed; a revived Instance cannot reuse that cleanup proof.

The framework records native ancestry only. All load-balancer, Factory URI, role, ownership and root restrictions remain in the authorization resolver. Initial scheduling pins identities; queued work reloads the Service, Stack, Instance, Agent, map, account and credential identities and rechecks current owner/schema authority, Key revision, expiry and revocation. Custom scoped grants still require the original root operation, and explicit child denials take precedence. This adds no general Agent access, system or Full bypass, Catalog/Host delegation, native route, role-field grant, public tool or approval bypass. The default `event:///instanceId=<id>` Factory relationship is required.

Local source validation reproduced five failures in six new regression methods against the frozen first repair, then passed 25 focused methods. The first full CI exposed a compatibility regression: existing verified Instance/Volume frames can omit their native process name, and the new predicate passed that permitted null to an immutable Set. The resulting mount exception also interrupted its normal authorization cleanup and affected later tests on the same thread. The predicate now treats absent names as a non-match; the Agent resolver separately requires a nonempty captured parent process before granting its new dependency authority.

The correction reproduced four failures, then passed all 54 originally failing CI methods and four affected guards in one JVM/main thread without resetting EngineContext. The workflow retains all 269 earlier required methods and adds 17 closure/provenance methods, for 286 required methods. C03 retains 1,396 operation tuples across 472 source inputs; its current source fingerprint binds the three changed runtime files, while historical producers and review chains remain intact. The first failed CI evidence and earlier local evidence are retained; corrected formal CI remains pending.

Formal CI, packaged-class/schema checks, publication, matching Server assembly and native TCP acceptance remain pending. Local source results do not establish those outcomes. The existing exact-root completion observer is unchanged: intentional nested authorization denial is not projected from arbitrary descendant metadata, and operation reads remain subject to current authorization. This candidate does not include the separate ordinary-Service dependency-link replacement work.
